# 旅さき — HTML版（サイト版）

ブラウザだけで動く旅程プランナーです。ビルド不要、素の HTML + ES モジュール。
地図は **OpenStreetMap**（Leaflet）を使います。

```
│   ├── hig-tokens.css  ← 配色（Apple のシステムカラー）

│   └── app.css         ← このアプリの並べかた
├── admin/              ← 管理画面（認証なし。公開する場所に置かない）
├── server/             ← APIキーを預かるバックエンドの参照実装
```

## 動かす

ES モジュールを使うため、`file://` では動きません。簡易サーバで開いてください。

```bash
cd web
python3 -m http.server 8000
# → http://localhost:8000
```

キーが未設定でも動きます（語句検索＋距離推定）。設定すると精度が上がります。

## テスト

```bash
cd web
node --test tests/*.test.js  # 552件（1〜2分かかります）
```

依存パッケージはありません。`npm install` も不要です。

画面のテスト（E2E）だけは、ブラウザが要るので別立てにしています。
本体に依存を増やさないためです。

```bash
npm i -D playwright-core && npx playwright install chromium
python3 -m http.server 8000 &
node tests/e2e/run.mjs      # 23件（2〜3分かかります）
```

単体テストが全件通っている状態でも、「データ読込中にボタンを押すと
行き止まりになる」は残っていました。関数が全部正しくても、画面が
繋がっているとは限りません。詳しくは `tests/e2e/README.md`。

単体テストは全件で1〜2分、E2E は2〜3分かかります。実行時間に制限の
ある環境では、`node --test tests/planner.test.js` のように分けて
走らせてください。

## 処理の流れ

ご提案いただいた「AIが案を出す → 調べる → 時間を確認 → 再計画」の順にしています。

```
希望文
  ↓ ai.js            意味を読み取る
  ↓ kb.js            知識ベースを検索・到達できる旅先に絞る
  ↓ ai.js            案を出す                     ← 1回目
  ↓ routes.js        実際の移動時間を取得（1リクエスト）
  ↓ verify.js        営業時間・期限と突き合わせる
  ↓ ai.js            問題の理由を渡して直させる      ← 2回目
  ↓ verify.js        それでも収まらなければ後ろから削る
  ↓ planner.js       時刻を割り付ける
旅程 + 地図
```

**AI = 意味の理解と選定 / プログラム = 制約処理** という分担です。モデルには
時刻計算をさせず、モデルが返した ID は必ず候補集合と照合します。

## AIの精度のために入れたこと

**構造化出力（`responseSchema`）。** 「JSON だけ返して」と頼むのをやめ、
形をモデル側で強制します。前置き・コードフェンス・閉じ忘れが消えました。
検索（グラウンディング）と併用できないので、検索を使うときだけ外します。

**役割は `systemInstruction` へ。** 同じ禁止事項をプロンプトの先頭に
書いていたときは、後ろに続く長い候補一覧に引きずられて薄れていました。

**候補の見せかたを厚く。** 名前と70字の説明だけを渡していたときは、
「海が見たい」に山の展望台が混じりました。分類・知名度・ジャンルの札を
添え、説明を140字まで伸ばし、1エリアあたり16→28件に増やしています。

**温度を下げました。** 希望の読み取りは 0.3 → 0.1（当てものではない）。
選定は 0.6 → 0.35（0.6 は「候補にある id」を書き崩すことがありました）。

**読めなければ、一度だけ作り直させる。** 混雑時に切り詰められた応答が
返ることがあります。そこで黙って諦めると、AIを設定しているのに
語句検索の結果が出ます。温度0でもう一度だけ聞きます。

## 行き先の数

「行ったのに、昼過ぎで予定が終わった」を減らすための変更です。

| | 以前 | いま |
|---|---|---|
| 1日あたり（ゆったり／標準／詰込） | 3 / 4 / 5 | 4 / 5 / 7 |
| 日帰りの上限 | 8 | 11 |
| 泊まりの上限 | 30 | 48 |
| モデルに見せる候補（1エリア） | 16 | 28 |
| 候補に挙げるエリア | 8 | 10 |
| 知識ベースの検索幅 | 160 | 260 |

多めに出しても、入りきらないぶんは `verify.js` が後ろから削ります。
足りないぶんを後から足すことはできないので、多めに出すほうが埋まります。

あわせて、**日帰りのときだけ移動の重みを上げました**（0.35 → 0.95）。
泊まりなら初日の3時間は翌日以降で取り返せますが、日帰りは取り返せません。
往復5時間の旅先を選ぶと、その日は2〜3か所で終わります。
「その日、実際に何か所まわれるか」（`fittableSpots`）も順位に入れています。

## 今回入れた構造変更

### 1. 出発地・最終目的地・帰着地を分離

```
□ 出発地に戻る          東京 → 鎌倉 → 江の島 → 東京
□ 最終目的地で終了       東京 → 名古屋（片道）
□ 別の場所へ帰る         東京 → 箱根 → 横浜
```

宿泊地とチェックイン期限も持てます（`trip.js` の `TripEndpoints` 相当）。

### 2. 営業時間・到着期限を制約として先に処理

「17:30 到着・17:00 閉館」は候補の時点で落ちます。落ちた理由は保持され、
2回目のプロンプトに入るので、モデルは同じ失敗を繰り返しません。

### 3. 食事の時間を検証時に確保

後から空きに差し込む方式だと、予定が詰まった日に食事が消え、押し込むと
帰りの便に間に合わなくなります。最初から時間を取っておけば、どちらも起きません。

### 4. Routes API は経路全体を1リクエスト

`computeRoutes` に `intermediates` をまとめて渡し、`legs[]` で各区間を受け取ります。
6スポットなら 7区間 → **リクエスト1回**。`optimizeWaypointOrder` は既定で off
（上位SKU回避。順序はこちらのスケジューラが決めます）。Route Matrix は使いません。

### 5. 食事・宿泊は Googleマップ/トラベルへ

在庫や価格を持たない領域なので、時間枠だけ確保して実際の店選びは外部へ渡します。

- 昼食・夕食 → その地域のレストラン一覧（地図）
- 宿泊 → Google トラベルのホテル検索（**チェックイン/アウト日付つき**）
- スポット → 地図 / Wikipedia / OpenStreetMap

## 画面（デスクトップ向け）

左に条件、右に地図と旅程の2カラムです。条件を直しながら結果を見る操作で
スクロールが要らないようにしています。1100px 未満では左を細く、860px 未満では
1カラムに切り替わります。

入力項目は次の5つだけに絞りました。

| 項目 | 内容 |
|---|---|
| どんな旅にしたいですか | 自由記述（例つき） |
| どこから出発しますか | 全国78か所から入力補完 |
| 旅の終わりはどこですか | 「出発地に戻る」/「別の場所で終える」の2択 |
| 出発・到着 | 到着は「この時刻まで」の期限として扱います |
| 興味 | 任意・複数可 |

**外した項目**

- **予算** — 効いていたのは入場料の合計だけで、交通費や宿泊費の実額を
  持っていない以上、判断材料になりませんでした。表示すると「考慮されている」
  という誤解を生むので外しています。
- **提案の方向性（定番⇔穴場）** — 内部では引き続き定番と穴場を混ぜており、
  スライダーを触らなくても穴場は必ず入ります。操作させる必要がありませんでした。
- **「出発地／終わり方／帰着地」の3項目** — 意味が重なっていたので、
  「旅の終わりはどこですか」の1問にまとめました。

## 希望に応えられなかったときに、そう言う

「富士登山をしたい」と入力して河口湖周遊が出てくると、なぜそうなったのか
分かりません。収録が無いのか、時間の都合で外れたのか、単に選ばれなかったのか。

そこで結果画面に、次のどれなのかを明示します（応えられている場合は何も出しません）。

- **収録されているが、今回は入らなかった** — どこにあるか、どうすれば行けるかを併記
- **そもそも収録が無い** — 見つからなかったことをはっきり書く

あわせて、季節で成立しないものは警告します。冬に富士登山を指定すると
「登山道が開いているのは概ね7月上旬〜9月上旬です」と出ます。

## 実際に見つけて直した不具合

ブラウザで動かして初めて分かったものです。

| 症状 | 原因 | 対応 |
|---|---|---|
| 「富士登山」で河口湖が出る | 富士山が収録されていなかった | 富士山エリア（五合目・吉田ルート等6件）を追加 |
| 強い一致1件の町が、良い一致3件の町に勝つ | 上位N件の *平均* で評価していた | 減衰つきの加重和に変更 |
| 「温泉でゆっくり」で日帰り湯のある山が選ばれる | 地域自体のジャンルを見ていなかった | 希望ジャンルと地域ジャンルの一致を加点 |
| 「スキューバダイビング」が「ハーバーランド」に一致 | 2文字ずつ機械的に切っていた（「ーバ」） | カタカナ・漢字は語のまとまりで取り出す |
| 該当なしでエラー終了 | 一致ゼロで例外を投げていた | 代わりの案を出し、応えられなかったことを明示 |
| プレースホルダーと結果が重なる | `display:flex` が `[hidden]` に勝っていた | `[hidden]{display:none!important}` |
| 日時入力が右端で欠ける | 400px を2分割していた | 縦に並べる |
| 地図が読めないと灰色の四角 | 失敗を黙っていた | 理由を書き、旅程は使えると伝える |
| 東京から片道8時間の旅先が日帰り候補に | 地域の到達可能性を見ていなかった | `reachableRegions` を追加 |
| 帰りの便が期限を過ぎて出発 | 検証NGでも旅程を組んでいた | `trimToFit` で収まるまで削る |
| 「全スポットが収まった」と誤表示 | 終点超過が件数から漏れていた | 削除件数から集計 |
| 昼食が入らない | 空きがある時だけ差し込んでいた | 検証時に時間を確保 |
| 片道の旅で候補が全滅 | 到達判定が往復前提だった | 終点までの時間で判定 |
| 1地域1スポットしか出ない | 検索語に一致したものだけを候補に | 地域決定後は全スポットを候補に |

## APIキーとモデル（`js/config.js`）

ご指定どおり、キーはプログラム内で固定です。設定画面はありません。

```js
export const GEMINI_API_KEY = "";   // ここに貼る
export const MAPS_API_KEY   = "";   // Routes API を有効にしたキー
export const KB_INDEX_URL   = "";   // 空なら同梱サンプルで動作
```

### モデル

```js
export const MODEL = "gemini-3.7-flash";
export const FALLBACK_MODELS = ["gemini-2.5-flash", "gemini-2.5-flash-lite"];
```

`FALLBACK_MODELS` は、契約やリージョンの都合で `MODEL` にアクセスできなかった
場合に順に試す控えです。旅程作成がそこで止まらないようにするためのもので、
実際に使われたモデル名は画面の「検証メモ」とブラウザのコンソールに出ます。

**埋め込み（検索用ベクトル）は `gemini-embedding-001` 固定**です。生成モデルとは
別系統のためで、1回の検索につき1回だけ呼びます。

### キーを固定することの意味

ブラウザから呼ぶ以上、**キーはページを開いた人から見えます**。ご指定なので
そのように実装していますが、公開サイトにするなら Cloud コンソールで

- **HTTPリファラー制限**（自分のドメインのみ）
- **APIの制限**（Routes API のみ）

を必ず設定してください。これが唯一の防御です。

## 残る制約

- **営業時間・料金は分類ごとの目安**です（同梱サンプルは手作業で確認した実データ
  なので、そちらは目安ではありません）。改善するなら Places API ですが課金が
  高くなりやすいため、組み込まず判断をお任せしています。差し替えるのは
  `feasibility.js` の `profileOf` 一箇所だけです。
- **地図タイルは OSM の公共サーバ**です。個人利用の範囲を超える場合は
  タイル提供元を変更してください（`config.js` の `TILE_URL`）。
- **実データでの取得・埋め込み生成は未実行**です。この環境からは Wikidata にも
  Gemini にも到達できないため、ロジックはすべてオフラインのテストと
  ブラウザ実機（同梱サンプル）で検証しています。
- 自然言語での旅程編集（「報国寺を外して」）はまだありません。今の構造なら
  `verify.js` の再検証を回すだけで足せます。

## 今回の3点（ご指摘いただいた件）

### 1. 観光地を調べられるようにしました

画面上部に「観光地を調べる」を足しました。地名・スポット名・分類で
収録データをそのまま検索できます。

| 入力 | 結果 |
|---|---|
| 四国 | 四国4県の収録33件（うどん・渦の道・金刀比羅宮…） |
| 香川 | 香川県の14件 |
| 道後温泉 | 道後温泉本館ほか、松山・道後の5件 |
| 城 | 名前に「城」を含む22件 |
| 屋久島 | 「該当がありませんでした」 |

エリアとジャンルでも絞れます。名前を押すと詳細が開き、地図が該当地点へ寄ります。

**この機能を足した理由**は、「四国が出てこないのは収録が無いからか、
選ばれなかっただけか」を、利用者が自分で確かめられなかったためです。

### 2. 「四国の有名な観光地を巡りたい」で銚子が出た件

原因は2つありました。

**(a) 四国が1件も収録されていませんでした。**
「四国」はどのスポット名にも含まれないので語句検索の一致がゼロになり、
「何でもいいから返す」経路に落ちて銚子が出ていました。四国7エリア
（松山・道後／高松／琴平／高知／徳島・鳴門／祖谷渓／直島）を追加し、
あわせて金沢・広島宮島・博多・長崎・札幌・函館・仙台松島・伊勢・那覇・
名古屋・大阪・浅草・高山・白川郷・別府・出雲・松本上高地も入れました。

**23エリア118スポット → 47エリア232スポット** になっています。

**(b) 地名を、他の検索語と同じ扱いにしていました。**
ジャンルは「近いもの」で代用できますが、地名は代用できません。
`areas.js` を足して、地名は先に解釈するようにしました。

- 収録がある → **その範囲だけ**から選ぶ
- 収録が無い → 提案の前に「収録がありません」と明示する

「屋久島の縄文杉を見たい」なら、地名の形をしていて収録のどこにも
現れない語として「屋久島」を名指しし、そのうえで代わりの案を出します。

### 3. Google Maps API が入らなかった件

キーが効いていないとき、これまでは黙って距離推定に落ちていました。
何が起きているか分からないので、次を足しました。

- 左パネルに **「APIキーの状態」**（設定済み／未設定を末尾4桁つきで表示）
- **「接続を確認」** ボタン — 1リクエストだけ送って結果を日本語で返します

403 が返った場合は、原因になりやすい4点を具体的に挙げます。

1. Routes API が有効化されていない
2. 請求先アカウントが紐付いていない
3. キーのAPI制限に Routes API が入っていない
4. HTTPリファラー制限に、いま開いているURLが入っていない

**キーを書く場所は `js/config.js` の1か所だけ**です（ご指定どおり固定）。
保存後はブラウザの再読み込みが必要です。詳しくは **[API_KEYS.md](API_KEYS.md)** に
まとめました（403の原因の切り分け、費用の考え方、リファラー制限の設定）。

## 泊まりの旅程が壊れていた件

画面のスクリーンショットにあった

> 9泊10日 / 4スポット / 所要225時間45分 / 余裕12951分

は、10日間を**1本の連続した時間**として扱っていたことによるものです。
夜になっても時計が止まらないので、深夜も観光し続ける計算になり、
「余裕」も10日先の期限との差で出ていました。

直したのは次の4点です。

**(1) 時計が日を意識するようにしました**（`verify.js`）
行動時間（9:00〜18:30）を越えたら宿に入り、翌朝から再開します。
食事も日ごとに数え直し、夕食は泊まる日にだけ入ります。

**(2) 立ち寄り数を日数に比例させました**
これまでは最大8か所固定でした。10日間なら1日3〜4か所×10日です。

**(3) 拠点を移せるようにしました**（`stays.js`）
収録6スポットのエリアに10日いても仕方がないので、日数に応じて
1〜4エリアを回ります。順番は移動が短くなるよう並べ替え、日数は
各エリアの収録数に応じて配分します。拠点が変わる日は朝に移動が入り、
その夜の宿はその日のエリアに取ります。

**(4) 予定が埋まらないことを検出するようにしました**
「10日間で4か所」のようなスカスカの旅程は `underfilled` として
検出し、その理由を添えてAIに作り直させます（キーがある場合）。

結果（東京駅発・9泊10日・「四国の有名な観光地を巡りたい」）:

```
徳島・鳴門 3日 → 松山・道後 3日 → 高松 2日 → 直島 2日
20か所 / 全日に予定あり / 帰着まで約2時間14分の余裕
```

# v3 の第一歩：調べるのを「私」から「AI」へ

## 何が問題だったか

前回、四国7エリアを収録して「四国で銚子が出る」は直りました。
ただ**それは私が四国を手で書いたから通っただけ**です。次に鳥取砂丘や
青森ねぶたを入れれば、まったく同じ失敗（関係ない土地が出る）が起きます。

収録を増やす方向には終わりがありません。ご指摘のとおり、
**AIが調べられる**ようにするのが正しい方向でした。

## どう変えたか

知識ベースを「唯一の正解」ではなく **「確認済みの土台」** に格下げし、
足りない土地はその場でモデルに調べさせて候補に加えます。

```
希望文
 ↓ areas.js    地名を取り出す
 ↓             収録あり？
 ├─ ある  →   その範囲から選ぶ（従来どおり）
 └─ ない  →   discover.js が AI に調べさせる
                ↓
              検証（下記）を通ったものだけ知識ベースに合流
                ↓
              以降は収録データとまったく同じ扱い
```

**ただしモデルの出力をそのまま旅程には入れません。** 通すのは検証済みのものだけです。

| 検査 | 落とす例 |
|---|---|
| 日本の範囲内か | 「東京都」と言いながらパリの座標 |
| 名前と座標が合うか | 「愛媛県」と言いながら東京駅の座標（都道府県の中心から◯km で判定） |
| 指定した地方の中か | 「四国」を頼んだのに神奈川県が返る |
| エリアとスポットが近いか | 鳥取砂丘のスポットとして大阪城 |
| 営業時間が成立するか | 開館20時・閉館9時 |
| 収録と重複しないか | すでにある松山城を二重に |
| 有効なスポットが2件以上あるか | 1件しか残らなかったエリア |

落としたものは件数と理由が残るので、「なぜ出てこないのか」を説明できます。

**調べたデータは「確認済み」とは区別します。** `source: "ai"` /
`verified: false` を持たせ、営業時間が入っていても `profileOf` は必ず
「目安」として扱います。旅程にも「AIが調べた◯エリア・◯スポットを候補に
加えました。営業時間・料金・場所は未確認です」と明記します。

同じ地名は `localStorage` に30日キャッシュするので、2回目からは呼びません。

**「観光地を調べる」タブでも同じです。** 該当0件のときに
「『◯◯』をAIで調べる」ボタンが出て、押すと調べて一覧と地図に出ます。

### 検証をテストで固定しています

モデルは呼ばず、応答を差し替えて検証だけを試します（`tests/discover.test.js`、12件）。

```js
// 「愛媛県」と言いながら東京駅の座標
validateDiscovered({ areas: [{ name: "でたらめ", prefecture: "愛媛県",
                               lat: 35.6812, lng: 139.7671, ... }] })
// → 採用0件 / 理由「愛媛県から◯◯km離れた座標」
```

### 正直に申し上げること

この環境から Gemini には到達できないため、**実際のモデル応答での動作確認は
できていません**。検証したのは、応答を差し替えたときの取り込みと棄却、
知識ベースへの合流、旅程への反映までです。キーを入れて
「APIキーの状態 → 接続を確認」が通れば、そのまま動くはずです。

# あわせて入れた、旅程エンジンの強化

いただいた優先順位（UIより先にエンジン）に沿って、⑭⑯⑰⑱⑲ を入れました。

## ⑰ 絶対条件と希望条件を分ける

`trip.must` を新設し、混ぜていたものを分けました。

```js
must: {
  spotIds: [],       // 必ず行く
  avoidSpotIds: [],  // 行かない
  meals: true,
}
```

効き方が根本的に違います。

- **希望条件**（静かな場所・海が見たい）は、点数が下がれば譲る
- **絶対条件**（18時までに帰る・ここには必ず行く）は、譲らない

`trimToFit` は時間が足りないとき後ろから削りますが、**「必ず行く」は
削りません**。削れるものが尽きたら削るのをやめ、`conflicts` として
理由を返します。プロンプトも【絶対条件】【希望条件】に分け、モデルが
落としても後段で必ず入れ直します。

到達判定も同じ扱いです。「四国」を指定していても「必ず行く」に鎌倉大仏が
入っていれば鎌倉が候補に残ります。そして**なぜそうなったかを書きます**。

> 「京都」をご指定でしたが、「必ず行く」の高徳院（鎌倉大仏）を優先して鎌倉にしました。

## ⑯ スポットを固定する

「観光地を調べる」の各行に「＋ 必ず行く」が付きました。押すと条件側に
チップとして並び、旅程から削られなくなります。

## ⑭ 「この旅程の弱点」

AIに自己採点させず、**プログラムで計算**します。

> **移動の割合** 旅程のうち移動が約53%（5時間2分）です。見学は3時間33分です。
> **歩く距離** 徒歩での移動は合わせて約7.6kmです。
> **待ち時間** 開館を待つ時間が合わせて約42分あります。
> **いちばん詰まっている日** 2日目が3か所でいちばん多い日です。

移動が45%を超える、8km以上歩く、といった場合は色を変えて出します。

## ⑱⑲ 「できません」→「どうすればできます」

行けないときに、**足りないのが何分なのかを計算して**押せるボタンにしました。

```
「四国」の収録エリアは、この日程では東京駅から往復できませんでした。

┌────────────────────────┬────────────────────────┐
│ 到着を1時間23分遅くする │ 1泊2日にする            │
│ あと1時間23分足りません │ 片道約5時間30分です     │
└────────────────────────┴────────────────────────┘
```

押すと入力欄が書き換わり、そのまま組み直します。旅程ができた場合も、
削った件数に応じて「到着を◯分遅くする」「ゆっくり回る」、予定が
埋まらなければ「日程を◯日短くする」を出します。

# 今回の修正と追加

## 1. ホテルが「とんでもないところ」に出ていた件

**原因はエリアの中心座標で宿を探していたことです。** 中心は収録スポットの
重心なので、富士山エリアなら山頂付近、祖谷渓なら谷底になります。
そこにホテルはありません。

`lodging.js` を足して、宿は次の順で決めるようにしました。

1. 利用者が指定した宿
2. そのエリアに泊まれそうなら、**駅・港などの人が集まる地点**
3. 泊まりにくいエリア（山・渓谷だけ）なら、**近くの町**に移す
4. どれも無くても、**中心座標だけは使わない**

「泊まれそうか」は収録データから機械的に出します。温泉地・街かどうか、
スポットの分類が山や渓谷ばかりでないか、駅があるか。祖谷渓のように
山しか無いエリアでは、近くの町へ移したうえで**その理由を書きます**。

> 祖谷渓には宿が少ないため、約28km離れた◯◯に宿を取ります

探すときの名前も直しました。「富士山 ホテル」で検索すると山を探しに
行ってしまうので、温泉地・街でないエリアは駅名（＝麓の町）で探します。

回帰テストで、**47エリアすべてについて宿の座標が中心と一致しないこと**を
確認しています。

## 2. Google Maps API のエラー

**Routes API は、公共交通（TRANSIT）に経由地を指定できません。**
エリア内を5か所まわる経路を TRANSIT のまま1リクエストで投げていたので、
400 INVALID_ARGUMENT が返っていました。これがエラーの正体です。

区間ごとに投げ直せば正確ですが、リクエストが区間数ぶんに増え、
「1リクエストに抑える」設計と衝突します。そこで

- **2地点の移動**（出発地→エリア、エリア→エリア、帰り）は TRANSIT のまま
- **経由地つきのエリア内の経路**は DRIVE に落として1リクエストのまま

とし、**落としたことを画面に明記**します。あわせて次も直しました。

| 直したところ | 理由 |
|---|---|
| 経由地が無いときは `optimizeWaypointOrder` を送らない | 指定自体が不正になる |
| DRIVE では `departureTime` を送らず `TRAFFIC_UNAWARE` を送る | 併用できない・基本SKUに収める |
| 路線名のフィールドは TRANSIT のときだけ要求する | 他モードでフィールドマスク不正になりうる |

キーが無くても送信前のリクエストの形は確かめられるので、
`tests/routes.test.js` で固定しました。

## 3. 混雑を避ける（持続可能な観光）

混雑は、行った人の体験を落とし、住む人の生活を圧迫します。旅程アプリが
直接効けるのは **時間をずらすこと** と **行き先を散らすこと** の2つです。

`crowd.js` が、次の要素から混みやすさを推定します。

```
知名度 × 曜日 × 時間帯 × 季節 × 場所の性格
```

- **並べ替え**：混みやすい場所を朝いちに回します。順番を変えるだけなので、
  行き先も移動距離も費用も減りません
- **表示**：各スポットに「ゆったり／ふつう／混雑／非常に混雑」を出します
- **旅程全体の見込み**と、住む人への負荷を減らす観点の注記

```
混雑の見込み  [██████████░░░░░]  混雑
· 混みやすい2か所を、人の少ない朝の時間帯に置きました。
· 1か所は知る人ぞ知る場所です。行き先が一点に集まらないほうが、
  現地の負担も軽くなります。
· 小町通りは特に混み合う見込みです。開館直後か閉館前が狙い目です。
```

**実測ではありません。** 混雑の実データは有料で取得も保証されないため、
検証できる要素だけで組み立てています。そのことは数字の隣に必ず書きます。

既定で有効ですが、スイッチで切れます。

# 海外と、特殊な要件に対応する

## 何が起きていたか

「パリで美術館をめぐりたい」と入れても「見つかりません」で止まり、

```
座標が日本の緯度経度の範囲外  → 弾く
都道府県名でない             → 弾く

```

前回入れた「AIが調べる」も、この検証の内側にあったので効きませんでした。
調べる前に地名として認識できず、調べても座標で弾かれていたわけです。

## どう変えたか

### 1. 地理の前提を、日本から地球ぜんぶへ（`geo.js`）

「日本かどうか」で分けるのをやめ、国に依らず次を確かめます。

| これまで | いま |
|---|---|
| 日本の緯度経度の範囲内か | 地球上の座標か |
| 都道府県名と座標が合うか | **国名または都道府県名**と座標が合うか |
| 時速120kmの陸路 | 距離で手段を分け、700km超は**空路**として計算 |

国の中心と半径は、よく行かれる60か国ぶん持っています。表に無い国は
**通しますが「照合できていない」と画面に書きます**。黙って通しません。

```
東京 → 博多    4時間36分（新幹線と空路の短いほう）
東京 → 台北    7時間38分
東京 → パリ   17時間09分（飛行12.5時間＋空港と入国審査）
```

### 2. 行き先そのものをAIに割り出させる（`resolveDestination`）

地名の辞書で照合する方式は、載っていない地名のぶんだけ黙って別の場所に
すり替わります。海外も、地名ですらない希望も扱えません。そこで
**割り出し自体をモデルにやらせ、返ってきた座標をこちらで検証**します。

```
「パリで美術館をめぐりたい」  → パリ（フランス）48.8566, 2.3522
「オーロラが見たい」          → トロムソ（ノルウェー）69.6492, 18.9553
「温泉でゆっくり」            → （地名なし。収録から選ぶ）
```

割り出しの段階でも矛盾は弾きます。「パリ」と言いながら国を「日本」と
名乗れば、その時点で不採用です。

### 3. Google 検索を使わせる

学習した知識だけでは「いま何が開いていて、何が行われているか」に
答えられません。モデルの呼び出しに検索を付け、**参照したページを画面に
出します**。

```js
// js/ai.js
if (search) body.tools = [{ google_search: {} }];
```

割り出しと調査の両方で使い、結果に出典（リンク）を添えます。

## 海外で新たに直したこと

海外を通してみて初めて出た不具合です。

| 症状 | 原因 | 対応 |
|---|---|---|
| 深夜2時に着いて「開館まで7時間待ち」で候補が全滅 | 到着時刻から観光を始める計算 | 深夜・早朝に着いたら朝まで待つ（夜着はその晩を宿に） |
| 帰りの便の後ろに宿泊が入る | 移動で1日ずれても日数を暦と合わせていなかった | 出発日からの経過日数で数え直す |
| まだ着いていない夜に宿代を計上 | 泊数ぶん機械的に宿を入れていた | 到着前の夜は「移動中（機内泊）」にして課金しない |
| 交通費が東京〜パリ片道14万円超 | 鉄道の運賃式をそのまま伸ばしていた | 700km超は空路の式に切り替え、安いほうを採る |
| キー未設定で「パリ」が黙って徳島に化ける | カタカナの地名を地名として拾えていなかった | 2文字以上のカタカナも地名候補にし、調べられない旨を明示 |

## 扱えないことは、扱えないと書きます

海外の旅程には、旅程エンジンでは計算できないことが付いてきます。
黙っているより、何が要るのかを書いたほうが役に立ちます。

> - フランスへの渡航には、パスポートと（国によっては）査証が要ります。
> - 移動時間には空港での手続きを含めていますが、便の時刻までは見ていません。
> - 料金は現地の相場から円に換算した概算です。為替で変わります。
> - 現地の時計は日本より、おおよそ8時間遅れています。旅程の時刻はすべて
>   同じ時計で計算しているため、現地時刻とはずれます。

ハワイのように日付が変わる渡航では「日付は1日戻ります」も出します。

## 確認したこと・していないこと

**したこと**（`tests/overseas.test.js` ほか、全203件）

- 割り出し → 調査 → 検証 → 旅程化 の全経路を、**モデルの応答だけ
  差し替えて**通しています。検証のコードは本物です
- 「フランスと名乗って南米の座標」「地球外の座標」「頼んだ国と違う国」を
  弾くこと
- 機内泊・帰着の期限・交通費の桁が現実的であること
- 「オーロラが見たい」から トロムソ（ノルウェー）の旅程になること

**していないこと**

- **実際の Gemini 応答での動作確認**。この環境から Google に到達できません。
  検索を使う指定（`tools: [{google_search: {}}]`）も、リクエストの形までは
  テストしていますが、実際に検索が走るかは未確認です
- 航空便の実時刻・実運賃。距離からの概算です
- 時差の正確な値。経度からの推定なので1時間ほどずれます（そう明記しています）

# 「収録がありません」で止めない／APIを食わせない

## 1. 名指しされた場所を、必ず調べにいく

いただいた画面では、

> 北海道の有名な観光地を周遊して、観光したい。雄信内のゴーストタウンを見たり、
> 航空自衛隊千歳基地や、宗谷岬、知床、青い池と…

に対して **「宗谷岬・ゴーストタウンは収録がありません」** と返し、
札幌・函館だけで組んでいました。

**原因**は、調べにいく条件の書き方でした。

```
日本のエリアが1つでも当たった → その範囲から選ぶ（＝調べない）
```

「北海道」という**地方名**が当たった時点で打ち切られ、名指しされた
宗谷岬・知床・青い池は**ひとつも調べていない**のに「収録がありません」と
答えていたわけです。当たったのは地方名で、頼まれたのは個々の場所でした。

**直したこと**: 名指しの場所は、収録の有無や地方名の一致にかかわらず
調べにいきます。

```
北海道 …………… 収録あり（札幌・函館）
宗谷岬 …………… 調べる → 稚内エリア4スポット
知床   …………… 調べる → 知床エリア4スポット
青い池 …………… 調べる → 美瑛エリア4スポット
        ↓
宗谷岬 2日 → 知床 2日 → 美瑛・青い池 2日（12か所）
```

調べた場所は「頼まれたから」候補の上位に来ます（検索の点数ではなく）。

日程に対して名指しが多すぎるときは、**何を入れて何を入れなかったかを言います**。

> 名指しいただいた場所のうち、宗谷岬・知床・美瑛・青い池を調べて旅程に
> 入れました。ゴーストタウンは、日程に対して行き先が多くなるため今回は
> 入れていません。日数を延ばすか、行き先を絞ると入れられます。

「調べたうえで外した」と「そもそも収録が無い」は別のことなので、
言い分けるようにしました。

## 2. Routes API が食うのを止める

いただいた 4xx のグラフ（失敗率 0.5〜0.79）と画面の「経路が見つかりません」から、
原因が3つ見つかりました。

### (a) 徒歩の経路に、車用のパラメータを送っていた（4xx の主因）

`optimizeWaypointOrder` は**車と二輪でしか受け付けられません**。
徒歩の経路（コンパクトなエリアでは `pickMode` が徒歩を選びます）に
付けて投げると 400 が返ります。**車のときだけ送る**ようにしました。

### (b) 呼び出し回数が倍になっていた

案を作り直すと `verifyProposal` がもう一度走り、**捨てるほうの案の経路まで
取りにいって**いました。1回の旅程作成で3リクエストのはずが6です。

順序や取捨は距離からの推定で足ります。**実際の経路は、採用が決まった案に
対してだけ**取りにいくようにしました。

| | これまで | いま |
|---|---|---|
| 鎌倉・日帰り | 4回 | **2回** |
| 四国・3泊4日 | 6回 | **3回** |

同じ経路の問い合わせも、その場で覚えて2度投げません。

### (c) 呼んでも無駄な呼び出しをしていた

| 呼ばないようにしたもの | 理由 |
|---|---|
| 700km を超える区間 | 空路です。投げても経路は返りません |
| 失敗が2回続いたあと | 設定の不備は何度投げても同じです。**そのページを開いている間は呼びません** |
| 先すぎる日付の公共交通 | 時刻表が未公開です。同じ曜日・時刻の直近の日に置き換えます |

(c) の最後は、画面の **「経路が見つかりません」の一因**です。半年先・1年先の
日時で公共交通を問い合わせると、時刻表が無いので経路そのものが返りません。
所要時間に効くのは曜日と時刻なので、遠い日付は直近の同じ曜日に置き換え、
置き換えたことを画面に書きます。

### 何が起きたかを画面で見せる

「APIキーの状態」に、直前の作成での呼び出し状況を出します。

```
直前の作成での呼び出し: 3回 / 失敗 2回 / 失敗が続いたため停止中
```

「経路が見つかりません」も、理由を添えるようにしました。

> 経路が見つかりません — 指定の日時にその区間の公共交通が見つかりませんでした
> （時刻表が未公開の先の日付や、便の無い時間帯で起きます）

### 完全に止めるスイッチ

設定を直すまでのあいだ、課金だけが増えるのを止められます。

```js
// js/config.js
export const USE_ROUTES_API = false;   // 一切呼ばない（距離からの推定になります）
```

# 外部データの取り込み

いただいた2つのファイルを収録しました。

| 元データ | 件数 | 中身 |
|---|---|---|
| 国土数値情報 観光資源（国土交通省, P12） | 16,229 | 名称・座標・住所・資源タイプ |
| 観光資源台帳の KML | 2,638 | 名称・座標・住所・資源タイプ・URL |
| これまでの収録（手作業で確認） | 232 | 上記＋営業時間・料金 |

**収録 47エリア232スポット → 1,383エリア15,047スポット** になりました。

## 置き場所

2万件を `sample-data.js` に入れると数MBの JS モジュールになり、
読み込みが重くなります。`kb.js` に元からある**分割読み込み**に載せました。

```js
// js/config.js
export const KB_INDEX_URL = "kb/index.json";
```

読み込みは実測 **約0.5秒**（localhost・3.2MB）。読めなかった場合は
同梱の232スポットに落ちて、その理由を画面に出します。

ファイルを軽くするため、**エリアから決まる項目は持たせていません**
（エリア名・都道府県・ジャンル・Wikipedia名）。読み込むときに補います。
1件ずつ持たせると、同じ文字列の繰り返しだけで1MB以上増えるためです。

## 点の集まりを、旅程に使える形にする

このアプリは「エリア（拠点）→ その日に回るスポット」で組み立てるので、
点をそのまま入れても旅程になりません。次の順で整えています。

```
18,867件
  ↓ 座標が日本の範囲外のものを除外            −1件
  ↓ 住所に県名が無いものを、座標から補完      +155件
  ↓ 重複をまとめる                          −2,533件
  ↓ 市区町村でまとめ、14kmを超えたら分割      1,336のまとまり
  ↓ 数の少ないまとまりを近隣へ合流            行き場の無い3件を除外
  ↓ 1エリア40件までに絞る（知名度順）
15,047スポット / 1,383エリア
```

### 実際に直した取りこぼし

| 症状 | 原因 | 対応 |
|---|---|---|
| 宗谷岬・青い池が丸ごと消える | 件数の少ない市を足切りしていた | 台帳に載る場所は、近隣へ寄せられなくても残す |
| 台帳の156件が行き場を失う | 住所に県名が無かった（「帯広市西13条…」） | 座標から最も近い既知の点の県に合わせる |
| 「知床半島の海岸」が旅程に2回 | 同名でも離れていれば別物として残していた | 同名は距離に関係なく1件に |
| 「道後温泉の道後温泉本館」 | 修飾つきの表記を別物として扱っていた | 修飾を落として突き合わせ、近ければ1件に |
| 「斜里郡斜里町」というエリア名 | 郡をそのまま名前にしていた | 郡を落とす |
| 経度が 33.3（本来 133.3）の1件 | 元データの誤り | **推測で直さず除外**し、件数を報告 |

### 順位付けの作り直し

件数が65倍になったことで、これまでの並べ方が壊れました。

> 「四国の有名な観光地を巡りたい」→ **四国中央市**
> 　伊予三島秋祭り、かわのえ秋まつり、紙のまち資料館…

原因は2つです。

1. **地名を検索語にも使っていた** — 「四国」が地名として絞り込みに
   使われたうえ、語としても残り、名前に「四国」を含む
   *四国中央市* のスポットを大量に押し上げていました。
   地名は絞り込みだけに使い、語からは外します。
2. **当たった語の数しか見ていなかった** — 名前に当たったのか説明文に
   当たったのかを区別せず、知名度も見ていませんでした。1万件を超えると、
   名前に「温泉」を含む地元の小さな湯が草津や箱根を押しのけます。
   当たった場所で重みを変え、知名度を控えめに効かせるようにしました。

直したあと:

```
四国の有名な観光地を巡りたい      → 直島・高知（地中美術館、高知城、桂浜…）

北海道の有名な観光地を周遊したい  → 札幌市（北海道神宮、開拓の村…）
```

# 公共交通を、車で代用するのをやめました

前回、経由地つきの経路をこう処理していました。

```js
if (mode === "TRANSIT" && points.length > 2) {
  effective = "DRIVE";        // ← これが誤り
}
```

Routes API が公共交通に経由地を許さないのは本当ですが、**車に読み替えるのは
回避策として筋が悪い**です。

- 鉄道とバスで動く旅程を、車の所要時間で組むことになります
- とくに地方で外れます。**1時間に1本のバス区間を「車で10分」と見積もると、
  `verify.js` が「時間内に収まる」と判定した旅程が現地で破綻します。**
  このアプリが防ぐはずの失敗そのものです

「車の時間で見積もっています」と注記は出していましたが、注記で
埋め合わせられる種類の誤差ではありませんでした。

## 代わりにしたこと

区間ごとに分けて取ります。ただし全区間ぶん投げると費用が跳ねるので、
**どこに正確さが要るか**で配分します。

```
区間を並べる
  ↓ 徒歩でつながるひと続き（3区間以上）… まとめて1回（WALKは経由地が使えます）
  ↓ 残りを長い順に、予算の範囲で    … 1区間ずつ公共交通で
  ↓ 予算を使い切った先              … 距離からの推定（そう明記します）
```

**長い区間を優先します。** 徒歩5分が7分になっても旅程は壊れませんが、
バス1本を取り違えるとその日がまるごと崩れるからです。
1〜2区間だけの徒歩に1リクエスト使うのも割に合わないので、推定に回します。

上限は `js/config.js` で変えられます。

```js
maxTransitRequests: 10,   // 旅程1回ぶんの通し。経路ごとではありません
walkableKm: 1.4,          // これ以下は徒歩としてまとめる
```

## 費用はどうなったか

| | 前回（車で代用） | いま（公共交通のまま） |
|---|---|---|
| 鎌倉・日帰り | 2回 | **4回** |
| 四国・3泊4日 | 3回 | **9回** |

増えます。ただし **1回の旅程作成につき最大11回**（往路1＋上限10）で
頭打ちになり、案を作り直しても増えません（実際の経路は採用した案に
だけ取りにいくため）。所要時間を偽らないための費用だと考えています。
高すぎるとお感じでしたら `maxTransitRequests` を下げてください。
下げたぶんは推定に回り、そのことが旅程に出ます。

## テストの立て方を変えました

「車に読み替えていないか」を実際のリクエストで確かめようとしたところ、
APIキーが無い環境では1回も送られず、**テストが素通り**していました。

そこで「どの区間を、どのモードで、何回に分けて取るか」を決める部分を
`planLegRequests()` として切り出し、**投げる前の判断**を検証しています。
キーが無くても、車で代用していないこと・上限を守っていること・
長い区間を優先していることが確かめられます。

| 詳細 | 中央のカード | 下から立つシート（上角28px・すりガラス・85%まで） |

## 色を「面」と「文字」で分けた理由

ご指定のテラコッタ `#D4854E` は、クリーム地に対してコントラスト比が
**2.70:1** しかありません。文字色に使うと読めない（WCAG AA は 4.5:1 以上）
ので、役割で分けました。

| 役割 | 色 | 比 |
|---|---|---|
| 面（FAB・チップ・ティアの粒） | `#D4854E` | 上に載せる黒 `#2A2420` で **5.30:1** |
| 文字・線 | `#9F633A` | クリーム地に **4.53:1** |
| セージの面 | `#5A8F8C` | 帯・ルート線に使用 |
| セージの文字・線 | `#487270` | クリーム地に **5.00:1** |

ティアの色（砂金・ミント・テラコッタ）は**粒としてだけ**使い、
「定番」「知る人ぞ知る」「穴場」の言葉を必ず添えています。
色だけで意味を伝えていません。

夜の色も、明暗を反転させたのではなく焚き火の側に寄せました
（背景 `#191411`、純黒は使っていません）。端末の設定と、画面の
トグル（🌙）の両方から切り替わります。

## 8画面の対応

| ご指定 | このアプリでの姿 |
|---|---|
| 1. ホーム／希望入力 | 背景にぼかした地図。「どんな旅にしたい？」と大きなテキストエリア。下に横スクロールの雰囲気チップ。下部に浮かぶ「✦ 旅程をつくる」 |

| 3. 生成中 | ピンが生えて波紋が広がるカード。4段階の進み具合と、いま何をしているかを文で |
| 4. 旅程結果 | 上に地図（角丸で浮かせています）、下に泡カードのストーリー。調整チップと採点パネル |

## 写真について

収録データ（国土数値情報・観光資源台帳）に写真はありません。そこで:

1. `art.js` が、場所ごとに**決まった**絵を作ります。名前から数を作り、
   分類ごとの色相の帯に落とします。乱数は使いません（開くたびに
   色が変わると、同じカードが別の場所に見えます）。海は青緑、
   温泉は橙、山は緑になります。
2. `photos.js` が、Wikipedia の要約API（キー不要・CORS可）から
   代表画像だけを取り、届いたぶんを絵の上に重ねます。

写真は飾りで、旅程の本体ではありません。オフラインでも、記事が
無くても、画面はそのまま出ます。取れた／取れなかったの両方を
30日キャッシュするので、同じ場所を何度も取りにいきません。

## 動きについて

- 画面の切り替え … 0.96 → 1.0 に少し膨らみながら現れます（300ms）
- カード … 上から順に立ち上がります（1枚ごとに42msずつ遅らせる）
- ピン … 地面から落ちてきて、波紋が広がります
- ルート線 … 出発地から順に描かれます（`stroke-dashoffset` を動かします）
- 背景の地図 … 34秒かけてゆっくり拡大縮小します

`prefers-reduced-motion: reduce` の環境では、これらを**すべて止めます**。

## 触れる的の大きさ

44px を下回るものを無くしました。セグメント、ジャンルのチップ、
日のタブ、シートの「閉じる」、調整チップ、すべて 38〜58px です。

## ④ 言葉で旅程を直す

```
「もっとゆっくり、もう1泊増やして、道後温泉本館は外して」
   ↓
ゆっくり回る、1泊増やす、道後温泉本館を外す——として組み直します。
```

**AIに旅程を作り直させません。** AIがやるのは「言われたことを条件の
書き換えに翻訳する」ところまでで、組み立ては、これまでと同じ
`verify.js` と `pipeline.js` が行います。AIに新しい旅程を自由に
作らせると、営業時間も移動時間も無視した、もっともらしいだけの
旅程が返ってきます。せっかく実時刻を突き合わせているのに、
その外側で崩されては意味がありません。

返ってきたパッチは必ず検証します。

- 旅程に無いスポットIDは通しません（`remove` も `keep` も）
- 知らないペースの語は無視します
- 泊数は ±14、降水は 0〜1、時間は ±600分 に丸めます

**AIキーが無くても動きます。** 日本語の言い回しから読み取れるぶんは
`parseEditLocally` が読み取ります。文は句（、。）で切ってから見ます。
「松山城は外して、温泉をもっと増やして」を一続きで扱うと、
「温泉」の近くに「外して」があるせいで温泉まで減らす指示に読めるためです。

同じ理由で、**場所の名前に含まれる語はジャンル判定から隠します**。
「道後温泉本館は外して」は、その1か所を外す指示であって
「温泉を減らして」ではありません。

## ⑤ 天気・日没・混雑での見直し

```
天気・日没・混雑から見ると                                    4件
 ・1日目: 日中は 22〜24℃。13時〜16時ごろに雨の可能性があります（最大 90%）。

 ☐ ☂ 2日目 13:40の「桂浜」は屋外です。この時間の降水確率は 90% なので、
      屋内の「県立美術館」に入れ替えられます。
 ☐ 🌇 3日目の「展望台」は 19:30 着ですが、この日の日没は 18:12 です。
 ☐ 👥 1日目の「高知城」は 14:57 着です。非常に混雑の時間帯なので…

              [選んだ 1件で組み直す]
```

**黙って変えません。** 雨だからと勝手に行き先を差し替えられたら、
楽しみにしていた場所が理由も分からず消えます。理由を添えて出し、
選ばれたものだけを条件に足して組み直します。

判断はすべてプログラム側です。「雨の時間帯に屋外のスポットが入って
いるか」は、降水確率と分類を突き合わせれば決まります。AIに聞くと、
同じ旅程でも聞くたびに違う答えが返り、理由も説明できません。

- 天気は **Open-Meteo**（キー不要・CORS可）。時間ごとの降水確率・
  気温・天気コードだけをもらいます
- 予報の効く16日を超える日付には**問い合わせません**（返らないので）
- 同じ日・同じ場所は3時間キャッシュします
- 取れなくても旅程は出ます。取れなかったことを画面に書くだけです
- 日没は `sun.js` の計算です（通信も課金もありません）
- 「屋根があるとは限らないもの」（市場・商店街）は雨の代わりに出しません
  — 高知の日曜市は屋外です

## ③ 採点に、リズムと疲労の目盛りを足しました

**旅のリズム**: 同じジャンルが続くほど下がります。
寺 → 寺 → 寺 → 寺 は時間的には成立していても、旅としてつらい。
食事をはさむとそこで切れます（座って休めるので）。

**疲労**: 0〜100 の目盛りと段階の言葉（ゆったり／普通／やや疲れる／過密）。
80 を超えると「この旅程は人にはきつい部類です」と出します。
見ているのは5つ——いちばん長い1日、続けて歩く時間、1日に歩く合計、
休憩をはさまない見学の連続、朝の早さ。どれも数えれば決まる量です。

## 23時間41分の「自由時間」

最終日の帰りまで間が空くと、そこに1つの大きな「自由時間」を置いて
いました。上限が `24 * 60` 分だったため、夜をまたいで
**23時間41分の自由時間**ができ、採点にも
「いちばん長い1日は 29時間21分」と出ていました。

夜をまたぐ空きは自由時間ではなく「まだ予定を埋められていない日」です。
自由時間はその日の行動終了時刻（21時）で打ち切り、8時間を超えるものは
作らないようにしました。埋められていない日のことは、これまでどおり
`verify.js` の `underfilled` が別に伝えます。

## クリックイベントが「条件」として渡っていた

`run()` に条件を渡せるようにした際、
`addEventListener("click", run)` のままだったため、ボタンを押すと
**クリックイベントが旅の条件として渡り**、「出発地が見つかりません」で
止まっていました。`() => run()` に直しました。

# Apple のデザイン（HIG）への刷新

Material Design 3 で作っていたものを、Apple の Human Interface Guidelines
のやりかたに置き換えました。見た目の好みの話ではなく、**奥行きの出しかた**
が根本から違います。

| | Material 3 | Apple |
|---|---|---|
| 段の出しかた | 面の明るさ（surface container の階層） | 地をグレーにして、白いカードを置く |
| 境目 | 面の色の差 | 0.5px のヘアライン |
| 押した反応 | さざ波（ripple）が広がる | 全体が少し薄く、少し縮む |
| 影 | 浮くものに強めの影 | ほとんど使わない |
| 角 | 4/8/12/16/28px | 6/10/14/18/22px（大きいものほど丸く） |
| 強調 | 塗りのボタン＋色面ボタン | 塗りのボタンは画面に1つだけ |

## 配色

`css/hig-tokens.css` は、Apple のシステムカラーの公称値をそのまま
持っています（systemBlue `#007AFF` / `#0A84FF` など）。明るい配色と
暗い配色は、端末の設定に合わせて切り替わります。切り替えのボタンは
置きません。

地とカードは、Apple の grouped background の考えかたです。

```
grouped-bg  #F2F2F7 / #000000   画面の地
card        #FFFFFF / #1C1C1E   その上に置くカード
fill        8% グレー           入力欄・チップの塗り
separator   0.5px のヘアライン   区切り
```

後半で、これまでの `--md-sys-color-*` に割り当て直しています。
`app.css` は 1,100 行あり、全部を書き換えるより、意味の近いものに
繋ぎ直すほうが取りこぼしがありませんでした。名前は Material のまま
ですが、中身は Apple の配色です。

コントラスト比（明るい／暗い）:

| | 明 | 暗 |
|---|---|---|
| 本文（label / card） | 21.0 | 18.9 |
| 補助（secondary label） | 4.6 | 6.3 |
| 主色（blue / card） | 4.5 | 6.4 |

いずれも WCAG AA（4.5:1）を満たします。

## 入れた部品（`css/hig.css`）

すりガラスのナビゲーションバー、幅いっぱいの主ボタン、アイコンボタン、
4種のボタン（塗り／淡色／枠線／文字だけ）、カード、カプセル型のチップ、
塗りの入力欄、**セグメンテッドコントロール**（灰色の溝に白い錠剤）、

アラート、ボトムシート、**inset grouped list**（区切り線を文字の

クラス名は `md-*` のまま残しています。画面を組む JS が出す名前を

## 字

# 指摘への対応（初回UX・結果画面・プロキシ）

## 1. 入力を3段にした

「結局どこまで入れればいいの？」に、番号で答えます。

```
1  どんな旅？        ← ここだけ埋めれば作れます
2  いつ・どこから？   ← 初期値が入っています
   もう少しくわしく決める（畳んである）
   [ 旅程をつくる ]
```

## 2. 「到着」→「帰着」

内部では「旅の終点に何時までに着きたいか」でした。「到着」だと
どこへの到着か分かりません。名前を変えたうえで、いま何を指定して
いるのかを、そのまま日本語で出します。

```
日帰り・10時間・東京駅に19:00までに戻る
```

出発地・帰着時刻・「旅の終わり」のどれを変えても、この文が追随します。

## 3. 現在地は、押されたときだけ聞く

以前は `startHomeMap()` の中で `getCurrentPosition()` を呼んでいました。
何も操作していない相手に、いきなり「現在地を使用しますか？」が出ます。
何のために聞かれているのか分からないぶん、断られて当然です。

**「◎ 現在地から探す」を押したときだけ**取りにいきます。取れたら、
いちばん近い**駅**を出発地に入れます（`nearestPlace`）。緯度経度を
そのまま出発地にはしません。経路検索は駅を起点にするほうが実態に
合いますし、「新宿駅から」のほうが利用者にも確かめようがあります。

## 4. 結果画面を「要約 → 旅程 → 詳細」に

以前は、作った順（要約→適合度→ペース→出典→点数→混雑→費用→…→旅程）に
20個ほどのパネルが積まれていました。豪華ではあるのですが、旅行者が最初に
見たいのは「で、何時にどこへ行くのか」です。

```
要約（判断 → 数字）
3案
旅程                    ← ここまでが最初に見るもの
言葉で直す
この旅程を調整する
▸ この旅程をくわしく見る（11件）   ← 畳んである
```

分析は消していません。畳んだだけです。

**判断を数字より先に置きました。** 「無理のなさ 68/100」だけでは、
68が良いのか悪いのかを読み手が決められません。

```
少し急ぎめです
帰りの余裕 15分・無理のなさ 68/100
```

見るのは「無理がないか」だけにしています。適合度も混雑も点はありますが、
最初に知りたいのは「この予定で本当に回れるのか」です。順番を逆にすると、
帰れない旅程に「ご希望との相性 92点」と書くことになります。

## 5. プロキシの防御（`server/`）

**「APIキーを隠したから安全」ではありません。** キーを隠しても、入口が
誰でも叩ける状態なら、**プロキシ自体が無料のAPIとして使われます**。
請求は持ち主に来ます。CORS は止める役に立ちません。ブラウザの中でしか
効かない約束事で、curl やスクリプトには何の関係もないためです。

次の順に落とします（Cloudflare Worker / Node の両方）。

| | 内容 |
|---|---|
| 1. Origin | 設定していれば、そこ以外は 403 |
| 2. レート制限 | IPごと 20回/分・200回/時（既定） |
| 3. 本文の大きさ | 512KB を超えたら、読まずに切る |
| 4. 入力の中身 | モデル名・経路の起点終点をここで確かめる |
| 5. タイムアウト | 上流を30秒で打ち切る |

失敗の理由は外に細かく返しません（探られる材料になります）。

**`X-Forwarded-For` の先頭は信用しません。** 先頭は送り手が好きな値を
書けるので、「毎回ちがうIPを名乗る」だけでレート制限が素通りになります。
信じてよいのは、自分の逆プロキシが最後に足した1つだけです
（`TRUST_PROXY=1` のときだけ見ます）。Cloudflare 版は、偽装できない
`CF-Connecting-IP` を使います。

Node 版の既定も変えました。`ALLOW_ORIGIN` の既定を `"*"` から空にし、
**空のまま起動したら警告を出します**（設定し忘れたまま公開されるのを
防ぐため）。

## 6. データ読込中の行き止まりを直した

知識ベースは 3MB あります。読み終わる前に「旅程をつくる」を押されると、
これまでは「データを読み込めていません」で終わりでした。
押せない状態にして、ボタン自身に理由を出します。

```
旅先のデータを読んでいます…   → （読み終わると） 旅程をつくる
```

読めなかった場合も押せる状態に戻します。押せないまま理由も出ないのが、
いちばん困ります。

# 次点の指摘への対応

## 6. 3案の違いを、実際の旅程から拾う

「ゆったり／王道／探索」という名前だけでは、何が違うのかが分かりません。
名前に付いた説明は**作る前の方針**であって、出来上がったものとは
限りません。3案を並べて実際に比べ、いちばん際立っている点を1つ言います。

```
🌿 ゆったり                ⭐ 王道  [おすすめ]      🗺 探索
移動がいちばん短い
2か所・移動 4時間24分       3か所・移動 4時間46分     3か所・移動 4時間46分
立ち寄りを絞って…          定番を中心に…            穴場を多めに…
無理のなさ 66              無理のなさ 68            無理のなさ 66
```

**差がわずかなときは、何も書きません。** 5分の差で「いちばん短い」と
書くと、選ぶ側を迷わせるだけです（移動20分・件数1か所を境にしています）。
同じ案に2つの札は付けません。

見出しでも先に推します：**「あなたには『王道』がおすすめです」**。

**点は、いちばん小さく、いちばん最後に。** 以前は 66 / 68 を
カードの右上に大きく出していました。66と68を見比べても、どちらが
自分に合うかは決められません。

## 8 / 10. 「確認済み」と「最新」を分ける

3年前に確認した営業時間も「確認済み」ではあります。けれど、それを
最新と同じ顔で出せば、閉まっている店の前に立たせることになります。

```
確認済み 8件・AI調査 1件。公式情報を確認できていません。
→ 訪問前に、公式サイトで営業時間をご確認ください。

最終確認 2026/8/25（9日前）
```

鮮度は、旅程のうち**いちばん古い1件**で決めます。平均には意味が
ありません。10件のうち9件が今日のもので1件が3年前なら、困るのは
その1件です。60日を超えたものは、色を変えて言います。

## 9. 状態だけでなく、取るべき行動まで

「AI調査」とだけ出すと、「AIが適当に言っている？」と受け取られます。
言いたいのは「まだ裏が取れていない」です。

| | 言うこと | 次にすること |
|---|---|---|
| 🟢 確認済み | 確認が取れています | （なし） |
| 🟡 推定 | 実際と異なる場合があります | 時間に余裕を持ってお出かけください |
| 🟠 AI調査 | 公式情報を確認できていません | 訪問前に公式サイトでご確認ください |

## 16 / 17. 旅行中は、地図アプリへ一手で渡す

案内そのものを自前で作る必要はありません。地図アプリのほうがずっと
よくできています。ここでやるべきは、**引き渡しを一手で済ませる**ことです。

```
つぎは
鶴岡八幡宮

[ ➤ 現在地から「鶴岡八幡宮」へ案内 ]
```

## 19. エラーに「次にできること」を書く

何が起きたかだけを伝えても、読んだ人は止まります。多くの場合、
答えは**「そのまま旅程は作れます」**です。それを書かないと、

```

```

本当に止まるもの（知識ベースを読めない）にだけ、直しかたを書きます。
そこに「そのまま作れます」とは書きません。

## 13. 外部ライブラリの取り込み（`tools/vendor.sh`）

旅行サイトは移動中・低速回線・海外回線で開かれます。一般的なサイト
以上に「他所のサーバが遅い／届かない」の影響を受けます。それに、
CDN から読むかぎり**配られる中身が変わっても気づけません**。

```bash
sh tools/vendor.sh
```

Leaflet を `vendor/` に落として自分のサーバから配れるようにし、
あわせて SRI ハッシュを表示します。CDN を使い続けるなら、
表示された `integrity` を index.html に貼ってください。

**index.html にはまだ SRI を書いていません。** ハッシュは実物から
計算しないと意味がなく（合わない値を書くとブラウザが読み込みを拒みます）、
作業環境から CDN へ到達できなかったためです。上のスクリプトを
手元で流して、出てきた値を貼ってください。

# 公開前の指摘への対応（S項目）

## S-1. レート制限を、本当に数えられるものにする

**KV では数えられませんでした。** 「読む → +1 → 書く」をすると、
同時に来た2本が同じ値を読み、同じ値を書きます。

```
A: 20 を読む
B: 20 を読む      ← A はまだ書いていない
A: 21 を書く
B: 21 を書く      ← 2回通ったのに 1 しか増えていない
```

上限20のつもりが、束ねて投げれば何回でも通ります。従量課金の API を
後ろに置いている以上、「だいたい20回」では制限になりません。

**Durable Object に替えました。** 1つのIPにつき1つの実体が、
`blockConcurrencyWhile` の中で1本ずつ処理します。読んでから書くまでの
あいだに、別の呼び出しが割り込みません。`server/wrangler.toml`
（雛形）にバインドを書いてあります。

保持するのは「直近1時間の通過時刻」だけです。誰が何をしたかは
持ちません。1時間なにも来なければ、alarm で実体ごと消えます。

Node 版は1本のイベントループで動くので、`rateCheck` の中に `await` を
入れないかぎり割り込まれません。**そのことをコードに書いておきました**
（あとから await を足されると、同じ穴が開きます）。

Cloudflare 側の WAF Rate limiting も併用してください。上のものは
「Worker に届いてから」効きます。届く前に落とせるなら、そのほうが安いです。

## S-2. Origin の無いリクエストを弾く

ブラウザはクロスオリジンの POST に必ず Origin を付けます。付いて
いないということは、ブラウザから来ていないということです（curl・
スクリプト・他のサーバー）。空も弾くようにしました。

ただし **これは認証ではありません。** Origin は名乗りにすぎず、直に
叩く側は好きな値を書けます。素通りを1段減らすだけです。本気で守る
なら Turnstile かトークン発行が要ります（`server/README.md` に
「まだやっていないこと」として書いてあります）。

## CSP を入れた

`index.html` に `Content-Security-Policy` を書きました。
このアプリの外部依存が、そのまま一覧になっています。

```
script-src   'self' unpkg                     地図の部品
style-src    'self' 'unsafe-inline' unpkg fonts.google
font-src     'self' fonts.gstatic
img-src      'self' data: tile.osm upload.wikimedia
connect-src  'self' generativelanguage / routes / open-meteo / ja.wikipedia
base-uri 'none'; object-src 'none'; form-action 'none'
```

**script に `unsafe-inline` も `unsafe-eval` も要りません。** インライン
script はありませんし、`eval` も使っていません。style の
`unsafe-inline` だけは要ります（Leaflet が要素の style を直接書き
換えるため）。

効いていることは、E2E のほうで分かりました。Playwright の
`waitForFunction` が **CSP に止められて動かなくなりました**（中で
`eval` を呼ぶため）。テストのために CSP を緩めるのではなく、
テスト側を `page.evaluate` の手回しに書き換えています。緩めると、
テストしているものが本番と違うものになります。

`frame-ancestors` と `Referrer-Policy` は meta では効かないので、
公開時に HTTP ヘッダーで付けてください。

## innerHTML の入口を無くした

`el()` にあった `html:` の逃げ道を外しました。一度でも入口を作ると、
いつか誰かが AI の返答や外部データをそこへ通します。このアプリは
AIの文・Wikipediaの抜粋・利用者の入力を画面に出すので、全部が
入口になり得ます。

地図のピンも、HTML 文字列ではなく要素そのものを Leaflet に渡すように
しました（`divIcon` は 1.4 から HTMLElement を受け取ります）。
いまは安全な値しか入りませんが、「いまは」で持たせる作りにしないためです。

`innerHTML` は、コメント以外にコード上に残っていません。

## シートのフォーカス管理

`aria-modal="true"` は、支援技術に「これは前面のものです」と伝える
だけで、Tab の行き先までは変えません。Tab を押しつづけると、後ろの
旅程やフォームへ抜けていきました。見えているのはシートだけなので、
使う側からはフォーカスが行方不明になったように見えます。

- 開いたら、シートの中の最初の要素へ入れる
- 端まで来たら反対の端へ回す（外へ出さない）
- 閉じたら、開いたところへ戻す

最後のひとつが無いと、フォーカスが `<body>` に落ち、次の Tab が
ページの先頭から始まります。どこを読んでいたのかが分からなくなります。

E2E で「開いた直後はシート内 / Tab 30回でも外に出ない / 閉じたら
開いた場所に戻る」を確認しています。

## 設定画面を、使う人と作る人に分けた

「Gemini」「Routes API」は、こちらの都合の名前です。使う人が知りたい
のは「AIが効いているのか」だけです。

```
配色              端末の設定に合わせます
AIによる提案       使わない設定です（収録データから提案します）
実際の経路・所要時間 使わない設定です（距離から推定します）
収録データ         全国1383エリア・15047スポット
これまでの利用      0件（あと50件で確認）

▸ 開発者向け      ← ここに Gemini / Routes API / KB の状態
```

**キーの末尾4文字は出しません。** 見せても何もできませんし、キーと
いうものがあることを意識させる必要もありません。開発者向けの側でも
「設定済み／未設定」だけです。

## 現在地の使いみちを、ボタンのすぐ下に書いた

> 現在地は、いちばん近い駅を出発地に入れるためだけに使います。
> どこにも送りません。

# 自分で立てたモデルを使う（Gemma など）

`js/config.js` の `MODEL_PROVIDER` を `"local"` にすると、Google の API の
かわりに、自分で立てたサーバーを呼びます。

```js
export const MODEL_PROVIDER = "local";
export const LOCAL_MODEL    = "gemma3n:e2b";
export const LOCAL_BASE_URL = "http://localhost:11434";
```

```bash
ollama pull gemma3n:e2b
OLLAMA_ORIGINS=http://localhost:8000 ollama serve
```

OpenAI 互換の `/v1/chat/completions` を話すものなら何でも構いません
（Ollama / vLLM / llama.cpp server / LM Studio）。

## いちばん大きい違いは、課金が無くなること

経路検索はそのままですが、**AIの呼び出しは無料になります**。自分の機械で
動かすからです。`quota.js` の 50件ごとの確認も、実質かからなくなります。

## できなくなること（2つ）

| | Gemini | 自分で立てたモデル |
|---|---|---|
| JSON の形をモデル側で強制 | `responseSchema` で確実 | **できない** |
| Google 検索で裏を取る | できる | **できない** |

**1つめ。** 形を強制できないので、「この形で返して」と頼み、読めなければ
温度を下げてもう一度だけ聞く、という作りに落ちます（`callModelJson`）。
これは元から用意してあった道なので、動きます。

**2つめ。** 収録に無い土地を調べる `discover.js` が動きません。
黙って推測を返させるのではなく、**そもそも呼ばない**ようにしました。

```js
if (!canGround()) {
  return { ok: false, reason: "いまのモデルは検索による裏取りができないため、"
                            + "収録に無い土地は調べられません" };
}
```

「調べたつもりの推測」ほど困るものはありません。海外や、収録に無い
場所を扱いたいなら、そこは Gemini を使ってください。

埋め込み（意味検索）も止まります。語句検索に落ちます。

## E2B のような小さいモデルで大丈夫か

**このアプリの作りとは、相性が良いほうです。**

モデルにさせているのは「候補から選ぶ」ことだけです。時刻も移動時間も
プログラムが計算します。そして、**モデルが返した ID は候補集合と必ず
照合します**。存在しない場所を作られても、そこで落ちます。

```
モデルが返した picks
   ↓  候補にある id だけを残す（allowed.get(p.spotId)）
   ↓  足りなければ、選ばれたエリアから埋める
   ↓  verify.js が営業時間と移動時間で削る
旅程
```

小さいモデルで落ちるのは「選びかたの質」であって、旅程の成立性では
ありません。「なぜこの場所か」の文章が平板になる、希望との噛み合いが
少し鈍る、という形で出ます。旅程が壊れる方向には効きません。

実際に、偽のローカルサーバーを立てて端から端まで通しています
（希望の読み取り → 候補の選定 → 検証 → 旅程の表示）。

## ブラウザから直に叩くときに引っかかる2つ

1. **CORS。** Ollama は既定で他のページからの呼び出しを断ります。
   `OLLAMA_ORIGINS` にこのページの出どころを入れてください。
   入れないと、プリフライトで止まり、**画面には何も出ません**
   （実際にこれで詰まりました）。
2. **CSP。** `index.html` の `connect-src` に行き先を足してください。

どちらも、`PROXY_URL` 経由にすれば要りません。プロキシ側は
`LOCAL_BASE_URL` を環境変数で受け取ります。

```bash
LOCAL_BASE_URL=http://127.0.0.1:11434 \
LOCAL_MODELS=gemma3n:e2b \
ALLOW_ORIGIN=https://example.com \
node server/node-proxy.mjs
```

# 読み込みが 12.8秒 → 0.6秒 になった話

スポットを 18,685件に増やしたとき、「旅程をつくる」が押せるように
なるまで 12.8秒かかりました。データを増やしたせいだと思ったのですが、
測ってみると **知識ベースの読み込みは 154ms** でした。

```
index.json          7ms
シャード7枚の取得  184ms
JSON.parse          16ms
regions            33ms
loadKnowledgeBase 全体 154ms
```

原因は **Google Fonts の読み込み**でした。

**スクリプトは、先に書かれたスタイルシートの読み込みを待ちます。**
`fonts.googleapis.com` が遅い（この環境では届かない）と、地図だけでなく
**条件の入力まで待たされます**。

Web フォントは外しました。和文は Apple ならヒラギノ、Windows なら
游ゴシック、Android なら Noto が最初から入っています。わざわざ他所の
サーバへ取りに行く相手は、ごく一部です。そのごく一部のために、
全員が待たされていました。

あわせて、Leaflet の `<script>` に `async` を付け、シャードの取得を
並列にしました（1枚ずつ待っていた頃は、待ち時間が「往復 × 7枚」でした）。

# 画面からの指摘への対応

## 移動時間が短すぎた（「22時間が4時間」）

原因は3つありました。

**1. どこからでも飛行機に乗れることになっていた。**
700km を超えたら空路、という判定しかしていませんでした。松本から
網走が「時速800kmで4時間」です。実際には、まず空港まで出る時間が
かかります。主な空港の位置を持ち、**両端の70km以内に空港があるとき
だけ**空路を選べるようにしました。地方空港どうしは直行便がまず無いので、
乗り継ぎ1回ぶん（60分）を足します。

**2. 海の上をまっすぐ歩いていた。**
本州から北海道へは青函トンネル、四国へは瀬戸大橋、九州へは関門を
通ります。直線で結ぶと、津軽海峡を泳いで渡ることになります。
渡れる場所を経由した距離で計算するようにしました。
これを**距離の段階で**やらないと、700km未満の区間（大阪〜松山など）
で効きません。

**3. 速度が距離帯で不連続だった。**
40km が「在来線で145分」、64km が「鉄道で120分」。近いほうが遠い
ほうより遅い、という数字が出ていました。折れ線でつなぎ、
door-to-door の平均速度として滑らかにしました。


# 経路APIが「食うのに正しい時間を出さない」件

**`leg.duration` に、最初の電車を待つ時間が入っていませんでした。**

Routes API が返す `duration` は、乗ってから降りるまでです。9:00 に駅へ
着いて、次の電車が 9:35 なら、その35分は入りません。その値をそのまま
旅程に置くと、実際より早く着く前提で組むことになり、次の予定が押します。

必要な情報は、すでに取っていました。`transitDetails.stopDetails` の
`departureTime` / `arrivalTime` です。`summarizeTransitLeg` が待ち時間を
数えていたのに、**所要時間のほうがそれを使っていませんでした**。

```
出発時刻 → 最後に降りた時刻 → そのあとの徒歩
＝ 実際にかかる時間
```

「駅に着く時刻」と「目的地に着く時刻」も違うので、降りたあとの徒歩を
足し戻しています。分からないときは足しません（推測で埋めない）。

## 仕様の確認としてやったこと

| | 状態 |
|---|---|
| TRANSIT に `intermediates` は付けられない | 区間ごとに分けて取得 ✓ |
| `routingPreference` は DRIVE/TWO_WHEELER のみ | DRIVE のときだけ設定 ✓ |
| `optimizeWaypointOrder` は車と二輪のみ | 同上 ✓ |
| `departureTime` は未来でなければならない | 過去なら now+60秒 ✓ |
| 時刻表は先の日付ぶんまで無い | 45日を超えたら同曜日・同時刻の直近へ ✓ |
| 便の無い時間帯 | 運行時間帯へ寄せて1回だけ聞き直す ✓ |
| `transitDetails` は steps のフィールドマスクが要る | 15項目を要求 ✓ |
| **待ち時間は duration に入らない** | **← ここが抜けていました** |

# 位置情報「許可されていません」が、押していないのに出る件

原因は2つありました。

**1. https でないと、ブラウザは聞かずに断ります。** http のページでは
`getCurrentPosition` が即座に `PERMISSION_DENIED` を返します。利用者は
何も押していないのに「許可されていません」と出るので、自分が拒否したの
だと思ってしまいます。**先に `isSecureContext` を見て、別の文にしました。**

**2. `PERMISSION_DENIED` は「本人が断った」とは限りません。** 組織の設定、
拡張機能、端末側の設定でも同じコードになります。断定をやめました。

```
1 → このブラウザでは現在地を使えませんでした
     （設定・拡張機能・端末側で止められていることがあります）
2 → 現在地を測れませんでした（屋内や電波の届かない場所で起きます）
3 → 現在地の取得に時間がかかりすぎました
```

- **段の番号**は、その段に触れているあいだ、輪が広がります
- **生成中の点**は、いま動いている工程だけが脈打ちます
- **定番と穴場**は、寄っているほうの数字が大きくなり、反対側が薄くなります

すべて `prefers-reduced-motion: reduce` で止まります。

# 🔴 S 項目

## 1. 「なぜこの旅程なのか」を見せる（`fit.js`）

スポットごとに、軸ごとの点を出します。

```
🎯 希望との一致      ★★★★☆  80   ご希望の「温泉」に当たります
🚃 移動のしやすさ    ★☆☆☆☆  15   直前の場所から約42km
👥 混雑の避けやすさ  ★☆☆☆☆  22   非常に混雑の時間帯です
✦ 定番と穴場        ★★★★☆  76   誰でも知っている場所
```

旅全体でも同じことをします（「ご希望との適合度 69/100」）。
軸の並びは固定です。毎回入れ替わると読み手が比べられません。

**AIには採点させません。** 同じ場所でも聞くたびに点が変われば、
それは説明ではありません。

## 2. 情報の確からしさを3段階で（`confidence.js`）

```
🟢 確認済み … 収録データの実測値、または経路検索で取れた値
🟡 推定    … 分類ごとの目安、距離からの計算
🟠 AI調査  … AIが検索して得たもの。現地で変わっている可能性あり
```

スポットの営業時間にも、移動時間にも、それぞれ付きます。
同じ「約42分」でも、経路検索で取れたのか距離から計算したのかで
意味がまったく違うためです。

旅程全体では、**いちばん弱いものが全体の弱さ**になります。
9件が確認済みでも、1件がAI調査なら、そう言います。

## 3. エラーを旅行者の言葉に（`errors.js`）

```
🚃 正確な交通情報を取得できませんでした
   いまは通常時の所要時間から計算しています。旅程そのものは
   作成できますが、電車の乗換や待ち時間は実際と異なる場合があります。

   ▸ 技術的な詳細
```

開いた人だけが `Routes API 403: API_KEY_HTTP_REFERRER_BLOCKED` と、
その原因の見当を読めます。

キーが未設定なだけのときは「エラー」「失敗」と書きません。
設定していないのは選択であって、失敗ではないからです。

## 4. APIキーをブラウザに置かない（`endpoints.js` / `server/`）

`js/config.js` の `PROXY_URL` に自分のバックエンドを書くと、
**キーをヘッダーに載せなくなります**。

```
ブラウザ（キーを持たない）
   ↓  POST {PROXY_URL}/gemini/generate
   ↓  POST {PROXY_URL}/gemini/embed
   ↓  POST {PROXY_URL}/routes
自分のサーバー（キーはここだけ）
   ↓
Gemini / Routes API
```

参照実装を `server/` に置きました（Cloudflare Worker と、依存なしの
Node）。`https` でないプロキシは受け付けません（http だと通信の中身が
途中で読まれ、キーを隠した意味がなくなります）。

詳しくは `server/README.md`。**利用者ごとの上限も認証も
入っていない**ことを、そこに明記しています。

## 7. 3案から選ぶ（`variants.js`）

```
🌿 ゆったり  67    ⭐ 王道  63       🗺 探索  62
9か所・移動15時間  9か所・移動15時間  11か所・移動16時間
[おすすめ]
```

**どれがおすすめかは言います。** 3つ並べて放り出すのは、選ぶ手間を
押しつけているだけです。おすすめは `score.js` が数えた点で決めます。

ただし、**疲労が「過密」の案は、点が高くてもおすすめにしません**。
回れる数が多い＝良い、ではありません。

費用について。案ごとに一から作り直すと、同じ希望文をモデルに3回
読ませることになります。読み取りと検索用ベクトルは1回だけ計算して
3案で使い回し、**案を比べるあいだは経路も天気も取りません**。
採用が決まった案にだけ取りにいきます。

# 🟡 B 項目

## 14. 旅行中モード（`today.js`）

旅の当日は、旅程のいちばん上に「今日の旅」が出ます。

```
1日目 ・ 10:17 現在
次の予定
小町通り
10:21 から ・ あと 4分
食べ歩きと土産物の細い通り。鎌倉の賑わいはここに集まります。

        [「小町通り」に着いた]
```

長い旅程は当日ほとんど役に立ちません。スクロールして自分の現在地を
探しているあいだに、電車は出ていきます。当日に必要なのは
「次に何をすればいいか」だけです。

**遅れの数えかた。**「着いた」を押した時刻と、その予定の開始時刻の差で
数えます。「いまどこにいるか」で数えると、ゆっくり見ている人まで
遅れていることになるためです。

遅れているときは、**どこを削れば帰れるか**を出します。

```
40分 遅れています
「江ノ島」を36分 短くする、「長谷寺」を4分 短くすると、17:00着を保てます。

        [この形で組み直す]
```

削るのは**これから行く場所だけ**です（過ぎた予定は削れません）。
1か所から削るのは滞在時間の4割まで、残りが25分を切る削りかたはしません。
削っても間に合わないときは、**間に合わないと言います**。
できないことをできると言うのは、当日いちばんやってはいけないことです。

## 16. 情報の最終確認日時（`confidence.js`）

```
🟠 AI調査（3か月前に取得。変わっている可能性があります）
```

60日を超えたものには、古いと言います。取得日が分からないものには、
古いとも新しいとも言いません（それらしい日付を作らないこと）。
`discover.js` が調べたデータには、取得時刻を必ず刻みます。

## 17. その時期ならではのこと（`events.js`）

9月の京都と11月の京都は、同じ場所でも別の旅です。

```
城南宮・智恩寺・成相寺 — 紅葉の時期です。見ごろは標高と天候で
前後し、週末は道路も社寺も混みます。
```

扱うのは**時期で決まるもの**（桜・新緑・夏・紅葉・冬）だけです。
分類が合わないものには言いません（美術館に紅葉の話をしない）。

個別の催しの日程（花火大会、企画展）は持ちません。持てば必ず古くなり、
古い日程を自信ありげに出すのは、何も言わないより悪いからです。
そちらは AI が調べたぶんを `validateEvents` で日付と期間の重なりを
確かめてから使います。

## 12. 予約が要る場所（`confidence.js`）

```
⚠ 事前予約が必要です。訪問前に公式でお申し込みください。 [予約ページ]
```

`reservationRequired` が立っている場所だけ「必要」と言います。
分類から推せるもの（酒蔵・文化施設など）は「〜のことが多い分類です」
と書き、**断定しません**。要らない場所で予約を探させないためです。
予約URLは https だけ通します。

# 公開の準備と、旅行当日のための追加

ここまでで機能はそろっていましたが、**サイトとして人手に渡ったときに
最初につまずくところ**が残っていました。3つ入れました。

## 1. リンクを貼ったときに、何のサイトか分かる（OGP）

これが無いと、SNS でも社内チャットでも、URL がただの文字列として
貼られます。押す理由がどこにもありません。文章を1行増やすより効きます。

| 追加 | 中身 |
|---|---|
| `<title>` | 旅さき｜行きたいことから旅程をつくるAI旅行プランナー |
| `<meta name="description">` | 一言から、行き先・まわる順・移動時間まで組み立てます |
| `og:*` / `twitter:*` | 題・説明・カード画像（`og.svg`、1200×630） |
| `icon.svg` | ピンと星のマーク。タブの見出しと、ホーム画面のアイコン |
| `robots.txt` | `/admin/`・`/server/`・`/tools/` を拒否 |
| `sitemap.xml` | 1ページだけですが、置いておきます |

`og.svg` は文字を画像の中に焼き込んでいます。SNS 側でフォントが
無くても、同じ見た目になります。

**`robots.txt` は防御ではありません。** `admin/` に認証はありません。
公開する場所には置かないでください（`admin/README.md` にも書いています）。

## 2. 前につくった旅（`js/history.js`）

旅行サイトでいちばん戻ってくる導線が、ここにありませんでした。
ブラウザを閉じた時点で、作ったものは全部消えていました。

```
前につくった旅                      すべて消す
  箱根・小田原                  2日前   ✕
  神奈川県・6か所
  金沢                        8月27日  ✕
  石川県・8か所
この端末の中だけに残ります。どこにも送りません。
```

**旅程そのものは保存していません。条件だけを覚えて、押されたら
その場で組み直します。** 営業時間も混雑も日ごとに変わるので、
3か月前に作った旅程をそのまま出すと、閉まっている場所へ案内します。

出発日が過ぎていたら、日数と時刻を保ったまま、**同じ曜日の先の日**へ
ずらします。曜日を合わせるのは、休館日と混雑が曜日で決まるためです。

同じ旅（同じ題・出発地・日程）を作り直したときは、増やさずに上書きして
いちばん上に持ってきます。10件まで。`localStorage` だけを使います。

## 3. 電波が無くても開ける（`sw.js`）

このアプリがいちばん役に立つのは**旅行の当日**で、当日は電波の弱い
場所にいます。山の中、地下、海沿い、国外のローミング。

| 何を | どう |
|---|---|
| アプリ本体（HTML/CSS/JS） | 先に入れておく。更新があれば取りに行き、失敗したら手元のものを使う |
| 知識ベース（`kb/`） | 読んだものを残し、次は手元のものを先に返して裏で更新 |
| 地図タイル・写真 | **保存しません** |

地図タイルと写真を入れないのは、量が読めないうえ他所のものだからです。
端末の容量を黙って使うことになります。旅程の文字が読めれば、当日に
することは分かります。

`manifest.webmanifest` を足したので、ホーム画面に追加するとブラウザの
枠なしで開きます。

## あわせて直したもの

**貼り付いた「旅程をつくる」が浮いていた。**
`.pane-form` に `padding-bottom: 96px` を入れていました。帯のぶんを
空けるつもりでしたが、`position: sticky` は**親の content box の外へは
出られません**。空けたぶんだけ帯が浮き上がり、その下に次の項目が
透けて見えていました。sticky は流れの中に場所を持つので、そもそも
予約は要りませんでした。

**携帯で、押すために探す必要があった。**
狭い画面では `position: static` にしていました。並びのとおり下に流れる
ので重なりはしませんが、スクロールしないと押せません。画面下に
`fixed` で貼り付け、`body` の下余白で重なりを防いでいます
（sticky ではありません。親の中でしか効かず、結果まで下がると
消えてしまうためです）。セーフエリアも見ています。

**現在地から遠い駅を、黙って出発地にしていた。**
`nearestPlace()` は 200km まで許して、いちばん近い駅を返していました。
120km 先の駅を「現在地からいちばん近い駅」とだけ書いて入れると、
まったく違う土地から旅程が組まれます。`nearestPlaceInfo()` に変えて
距離も返し、30km を超えるときは距離を添えて注意を出します。
